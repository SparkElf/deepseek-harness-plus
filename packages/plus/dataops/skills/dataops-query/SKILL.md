# 问数

用户要「查数」「取数」「看数据」「出报表」时，按本技能执行。

## 触发

用户表达任何取数意图时**自动**使用，包括：查一下、统计、有多少、最近情况、拉个数据、出个报表。

## 一、取数前：先确认资源清单

**在真正执行取数前**，根据用户需求整理出这次要用的资源清单，并向用户确认。清单包含**两类**：

- **表**：数据来自哪些表（含库或 schema）
- **接口**：需要调用哪些 API 或 MCP 工具

确认时要做到两件事：

1. **补足缺失** —— 需求里隐含但你没列的资源（例如按地域筛选需要地域维表、按时间聚合需要日期口径）
2. **剔除冗余** —— 列了但这次用不上的资源

呈现用一张表，让用户能一眼核对：

| 资源 | 类型 | 用途 | 是否必需 |
| --- | --- | --- | --- |
| dwd_order | 表 | 订单明细 | 必需 |
| dim_region | 表 | 地域归属 | 必需 |
| query_api | 接口 | 调用取数 | 必需 |
| dwd_user | 表 | 本次不需要 | 建议剔除 |

用户确认前不要开始取数；用户补充或删减后，以确认后的清单为准。

## 二、选表策略

选表遵循三条规则，按顺序判断。

### 规则 1：有总表先用总表

存在覆盖完整范围的**总表**时，优先用总表，不要一开始就去翻分表。

### 规则 2：有地域区分时，先大后小

总表之外若按地域拆成多张表，**先用管辖范围大的，再用小的**，举一反三：

- 广西 与 南宁 → 先选广西
- 广西、南宁、青秀区 → 先选广西，不够再南宁，再不够再青秀区
- 全国 与 广西 → 先选全国

即：**层级浅的先选**，不要一上来就落到最细粒度。

### 规则 3：字段不满足才下探分表

只有当上一级表的**字段无法满足本次需求**时，才往下一级分表找。

需要下探的典型情形：

- 上一级表没有本次要的字段
- 上一级表该字段为空或不完整
- 需求明确要求了更细粒度的口径

**下探前要说明**：为什么上一级表不够，这次要落到哪一级。

## 三、查询超时：主动分批次

单次查询**超时**时，不要直接把失败抛给用户，而是**主动分批次**继续取：

1. 换一个更小的切分维度（时间区间、地域范围、ID 区间都可以）
2. 逐批执行，把结果合并
3. 完成后说明「因单次查询超时，已按某维度分 N 批取回」

分批时每批的规模要收敛到能完成的量；连续两批都超时，就把批次再拆细。

## 输出

取数完成后说明：

- 实际用了哪些资源（与确认清单对照）
- 从哪一级表取的数据
- 是否发生了分批，怎么分的
