# Agent Note: Move latest when a prerelease publishes

Status: proposed

[English](2026-09-18-move-latest-when-a-prerelease-publishes.md) | 中文

## Problem

Plus 家族里的每个包都发到 `next`，而 `latest` 一直停在原处。在 0.2.0-rc.7 发布之后对 `@sparkelf/dsh-plus-standalone` 实测：

```
latest   0.1.0-rc.35   2026-09-15
next     0.2.0-rc.7    2026-09-18
```

README 的安装行是 `npm install -g @sparkelf/dsh-plus-standalone`，它解析的是 `latest`。照做的人拿到的是本发行版形成今天这个形态之前的构建 —— 不同的插件、更旧的 supervisor，以及此后加入的补丁一个都没有。二十二个成员全部受影响，各自停在它最后一次设置 `latest` 时的版本上。

## Why it stayed invisible

**标签策略本身是有意为之且正确的。** 对含连字符的版本，`PlusFamily.distTagForVersion` 返回 `next`，因此预发布版绝不会意外占据 `latest`。这条规则是对的：向 `latest` 询问的消费者不应仅仅因为某个候选版最后发布就收到它。

**但从来没有任何东西去提升它。** 本仓库发布过的每个版本都带预发布后缀，于是这条规则每次都生效，而 `latest` 自第一次设置之后再未被写过。该策略没有毕业步骤，[npm release sequences](../../implemented/process/2026-08-10-npm-release-sequences.zh.md) 记录的发布序列也没提到它。

**从发布所监视的每一侧看，这个失败都是静默的。** 发布成功、镜像同步、每一项完整性检查通过、按名字安装也成功。只有省略标签的消费者拿到错误的构建，而他们的安装同样成功。

## Proposal

**在发布之后提升 `latest`，作为一个独立的阶段。**

`scripts/release/publish.ts` 新增 `promoteLatest` 与 `promoteFamilyLatest`，在发布运行结束时调用，也可通过 `--promote-latest` 单独执行。

- `distTagForVersion` 为 `latest` 的成员被跳过：它本来就发在那里。
- 先比较当前标签，因此已经正确的标签不会被重写。
- 提升发生在发布循环之后而非其中。此时集合完整且一致，因此失败留下的是一个已发布但标签陈旧的版本 —— 可用 `--promote-latest` 重跑补救 —— 而不是一个发布了一半的版本。
- 提升失败会点名无法移动的包与版本，并且不会把发布报告为失败。

## Findings this change rests on

1. **陈旧的远不止入口包，全部二十二个成员都是。** 审计读取了 `dist/npm` 里每个 tarball 的 `dist-tags`；每个都指向更旧的版本，多数停在 `0.1.0-rc.35`，另有一些停在 `0.2.0-rc.2`、`0.2.0-rc.4` 或 `0.2.0-rc.5`。
2. **规则正是防止意外提升的东西。** `distTagForVersion` 对带连字符版本返回 `next` 是正确的；缺口在于缺少一次刻意的提升，而不在于这条规则的存在。
3. **单独运行 `--promote-latest` 安全且幂等。** 对已发布的 rc.7 集合实测：22 个标签被移动，再跑一次会发现每个都已正确而一个也不动。
4. **标签正确之后 README 那条命令就能用。** 不带标签干净安装 `@sparkelf/dsh-plus-standalone` 装了 1011 个包并报告 `0.2.0-rc.7`；提升之前同一条命令解析到 `0.1.0-rc.35`。
5. **`npm dist-tag add` 是另一次写入，有自己的失败模式。** 它要求版本已存在，因此属于发布之后，且无法并入发布调用。

## Acceptance criteria

- 一次发布运行后，每个成员的 `latest` 都停在它发布的那个版本上。
- `--promote-latest` 只移动落后于成员版本的标签，且可安全重复运行。
- 以 `latest` 发布的成员不会被重新打标签。
- 提升失败点名该包并以非零退出，同时不把发布报告为失败。
- 不带标签安装成员，装到的是该次发布所发布的版本。

## Alternatives considered

**把预发布版直接发到 `latest`。** 否决：它让询问 `latest` 的消费者在候选版一发布就收到候选版，而这正是既有规则要防止的结果。

**去掉预发布后缀，让版本按常规规则发到 `latest`。** 否决：后缀是消费者区分候选版与定版的方式，也是版本方案赖以成立的东西。

**在发布循环内部提升。** 否决：循环已经幂等地处理单个成员的发布，而给每个成员再加一次 registry 写入，只会让被中断的运行更难推断，而不是更容易。

**等谁想起来时手工提升。** 否决：事情正是这样发生的。标签在三次发布、四天时间里一直是陈旧的。

## Risks

**提升会让发布候选版成为默认安装。** 对本仓库而言这就是意图 —— 它的每一次发布都是候选版 —— 也正是把提升做成具名步骤而非发布副作用的原因。同时发布定版的仓库会希望把提升限定为「版本不带后缀」。

**发布成功之后的提升失败是一种新的失败形态。** 发布已完成但标签没有，收尾需要 `--promote-latest` 而不是完整重发。提示信息点明了该命令的效果；它没有点出命令本身。

**标签是先读后写的。** 并发的发布者若在读写之间移动同一标签会被覆盖。本 scope 下没有别的东西在发布。
