# Agent Note：重新打包的工作区与其源比对，而不是与清单比对

Status: proposed

[English](2026-09-15-repackaged-package-verification.md) | 中文

## Problem

Plus 发行版以我们的 scope 重新发布二十个官方工作区，因为针对官方源码的补丁无法送达 registry 安装。从该机制首次发布到第四次修正之间，有四个缺陷进入了已发布的包，而它们在当时的检查下**全部通过**。

| 缺陷 | 评审时看到的样子 | 消费方遭遇 |
|---|---|---|
| 载荷列表缺少 `dist` | 每个清单都正确 | 服务器对每个页面返回 404 |
| 缺少 `cordis.patch.yml` | 每个清单都正确 | bundle 安装成功却不挂载任何东西 |
| 剥掉了 `dsh` 字段 | 每个清单都正确 | 二十个包加载不了；模型选择器从不出现 |
| 把我们的版本写进依赖范围 | 名字能解析 | 安装因一个不存在的发行版失败 |

当时存在的检查，是拿包与**其作者写下的清单**比对。清单无法报告作者没想到的东西，因此每个缺陷都以同样的方式被发现：安装结果，然后看它。

## Proposal

**一次重新打包运行为每个包与其来源工作区做比对，且该验证在发布命令内部执行。** 三个脚本构成一条命令。

1. `package-patched-official.mjs` 复制工作区发布的载荷，并把它的身份改写到我们的 scope。
2. `verify-patched-official.mjs` 将产物与源比对：当包遗漏了其工作区发布的载荷、丢掉了其工作区声明的清单字段，或引用了一个官方 registry 不提供的版本时，它失败。
3. `publish-patched-official.mjs` 按依赖顺序发布。

```sh
node scripts/release/republish-patched-official.mjs --source <built-checkout> [--version <semver>] [--dry-run]
```

版本从 checkout 推导。硬编码的常量每次运行都会漂移，把一次发布步骤变成一次手改。

## Findings this change rests on

1. **`dsh` 是包自身的声明，不是构建元数据。** `dsh.client` 注册一个浏览器模块，因此带它的包会被 web 应用加载，不带的包**装上了也被忽略**。剥掉它产生了二十个通过所有清单检查却什么都不加载的包。
2. **`cordis.patch.yml` 是 bundle 的组成。** bundle 的 `package.json` 在 `files` 里列出它，缺了它 bundle 不挂载任何东西。
3. **包的 `files` 列表是"它发布什么"的权威。** 拿打包产物与该列表命名的根目录比对，能抓到清单显示不出的遗漏——因为包自己的 `files` 列表仍然承诺着那个缺失的目录。
4. **重新发布的包保持官方依赖名与范围。** 构建后的代码 import 官方 specifier，官方 registry 提供这些范围；把我们的版本写进范围，等于命名一个不存在的发行版。以**上游版本**重发的运行范围本就正确，因此这项检查只适用于以我们自己的版本发布的修正。
5. **npm 只从项目自身的根读取 `overrides`。** 全局安装的 profile 不是根，因此写在那里的 override 被静默忽略；profile 安装自己的树，才使它成为那个根。

## Acceptance criteria

- 从载荷列表移除一个条目会让 spec 失败。
- 从剥离字段中移除 `dsh` 会让 spec 失败。
- 从载荷列表移除 `cordis.patch.yml` 会让流水线在验证器处失败。
- 发布命令执行打包、验证、发布，且**不存在跳过验证抵达发布的路径**。

## Alternatives considered

- **一份"要复制什么"的清单。** 否决：它正是失败了四次的东西。清单由漏掉遗漏的同一个作者写，而且没有任何东西执行它。
- **与官方 npm tarball 比对，而非与 checkout 比对。** 否决：checkout 就是发布已经产出的那次构建，与它比对无需网络，也不需要第二个事实来源。
- **发布后再验证。** 否决：已发布的版本无法撤回，且 registry 不会在同一名字下提供第二个包。

## Risks

- **验证器信任每个工作区的 `files` 列表。** 一个自身少声明载荷的工作区不会被抓到；这项检查检测的是重新打包时的遗漏，不是上游的打包缺陷。
- **版本锁定的构建决策会随上游升级而过期。** `allowBuilds` 命名精确版本，且 `verify-plus-governance` 固定该表，因此上游升级会让某个门禁失败，而不是静默跳过一次构建。

## Consequences

- **一次重新打包运行是一条命令。** 发布步骤不再是某个人凭记忆执行的一串操作。
- **新增一种载荷是被评审的改动。** 增加或移除一个条目会改变每个包所携带的内容，而 spec 明确列出了存在哪些条目。
