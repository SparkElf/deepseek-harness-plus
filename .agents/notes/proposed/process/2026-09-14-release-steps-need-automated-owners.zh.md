# Agent Note：发布与镜像是两步，而第二步可以自动化

Status: proposed

[English](2026-09-14-release-steps-need-automated-owners.md) | 中文

## Problem

一次发布写入了 npm，仓库运行的每一道门禁都报告完成。消费方却装不上。同一版本上有两处遗漏，产生了同一个症状。

第一处：大陆镜像提供的是同步副本，只有在它抓取之后才出现，而没有任何步骤请求过这次抓取。全新包的包文档返回 `404`，消费方从未解析过的包名的 tarball 也返回 `404`。这两者在发布者写入的 registry 上都看不到——那里立刻返回 `200`。

第二处：发行版声明的 npm 目标补丁从未被应用到 registry 安装。`dsh-plus start` 创建 profile 并启动服务，而补丁步骤只存在于 `dsh-plus apply` 里，后者需要 registry 安装并不具备的官方源码 checkout。于是由已发布补丁修复的缺陷，对命令行的每一个消费方都保持损坏。

两者在复发之前都已作为散文记录在本仓库的 Agent Notes 中。教训不是这些事实不为人知，而是：一个必须由人在多步发布的末尾记住的事实，最终一定会被那次发布丢掉。

## Proposal

给每一步一个无论是否有人记得都会执行的拥有者。

### 发布脚本同步镜像并证明结果

`scripts/release/sync-plus-mirror.ts` 为发布版本上的每个 Plus 成员请求一次抓取，并轮询直到镜像提供每一个；预算耗尽时让发布失败。它作为 `Release publish (Plus)` 的最后一步运行，因此消费方装不上的发布会让它所发布的那次工作流失败。

成员名来自 `releaseFamily('plus').members()`——与打包和发布所用同一套发现。另一份清单会与真正发出的内容漂移，而这种漂移直到消费方撞上缺失的包才会显现。

镜像请求是幂等的，重跑安全：一次排队的抓取与一个已提供的包都满足它。

### 独立安装会应用其发行版声明的 npm 补丁

`applyProfileNpmPatches` 由 `dsh-plus start` 在启动服务之前运行。它从发行版清单读取 `dshPlus.patchPackages`，把每个 `npm` 目标 variant 应用到 launcher 实际加载的已安装副本，并跳过反向已能应用的那些补丁。

它在每次启动时运行而不是只运行一次，因为重装会恢复已发布的字节，而 `npm` 目标补丁不改变任何版本号，其它机制不会注意到。

source 目标 variant 被跳过，而不是当作本函数的工作：它们需要 registry 安装并不具备的官方 checkout，而这半个补丁集的拥有者仍在 `dsh-plus apply`。

### 接线有自己的测试

只覆盖 `applyProfileNpmPatches` 的单元测试在该函数从未被调用时依然通过；把调用点换成 no-op 后所有既有测试仍然全绿。因此 `tests/standalone-cli-patches.spec.ts` 驱动构建后的命令，并断言补丁步骤确实运行过。删除调用后，它以“the command did not reach the patch step”失败。

## Acceptance criteria

- 当镜像未在预算内提供某个已发布包时，发布工作流失败。
- 通过镜像对已发布的 standalone 包执行 `npm install` 能得到可用的命令。
- registry 安装会在服务启动之前应用其发行版声明的每一个 npm 目标补丁。
- 独立启动对无法应用的 npm 目标补丁报告失败，而不是未打补丁就启动。
- 从 `start` 中移除补丁调用会让 `tests/standalone-cli-patches.spec.ts` 失败。

## Alternatives considered

- **更醒目地记录镜像步骤。** 否决：该事实已记录在本仓库中，而记录之后仍然失败的那次发布，正是“文档不是拥有者”的证据。一个必须在罕见的多阶段流程末尾恰好执行一次的步骤，正是自动化存在的形态。
- **要求操作者在宣布之前手动运行同步脚本。** 镜像提供之前发布不可安装，因此这一步属于发布工作流内部，而不是放在它旁边的 runbook 里。把它排在发布步骤之后，才能让部分失败表现为失败的工作流，而不是一次带着静默缺口的成功。
- **在创建 profile 时应用补丁，而不是每次启动。** profile 只创建一次，重装却不是。只在创建时打补丁会把补丁丢给第一次依赖安装，而缺陷正是在那个状态被发现的。
- **把 source 目标补丁当作本函数的工作。** 否决：它们需要官方 checkout。`dsh-plus apply` 拥有它们，独立命令不应在本做不到的工作上让每次启动都失败。
- **依赖 Windows coverage job 承担平台相关断言。** 它跑在上游仓库而不是本仓库，因此只在 Windows 出现的缺陷由用户而非 CI 发现。可注入的平台参数让断言能在测试套件真正运行的地方执行。

## Risks

- **镜像是第三方。** 它的可用性现在会卡住发布工作流。镜像中断会让一次 npm 已接受的发布失败；恢复方式是重跑该工作流的最后一步。
- **启动时的补丁应用是 shell 工作。** 需要存在 `git apply`，而发布前置条件为 Desktop 安装已经要求它。
- **陈旧的补丁会阻塞启动而不是降级。** 补丁不再匹配其目标的发行版会启动失败，直到补丁被退休或目标被重新钉版本。

## Consequences

- **消费方装不上时发布现在会失败。** 工作流多出一个镜像往返的开销；全新包可能需要一分钟其 packument 才出现。
- **启动时应用补丁，每次启动增加每个已声明补丁一次 `git apply`。** 它受发行版声明的补丁数量约束，且每个在已打补丁的树上是 `--reverse --check`。
- **不再能应用的补丁会让启动失败。** 这是有意的：静默地未打补丁启动，会把缺陷还给消费方却报告成功。
- **镜像被硬编码为默认值。** 从其它镜像安装的部署传入 `--mirror`。
