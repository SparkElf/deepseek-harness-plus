# Agent Note: 重建运行时镜像会保留本地提交

Status: proposed

[English](2026-09-13-runtime-mirror-preserves-local-work.md) | 中文

## Problem

运行时镜像位于 `~/.dsh/releases/plus/<build>`，它是一个 git 检出，同时承载着仓库里没有的工作：本地部署定制，以及尚未落地的修复。刷新部署时需要重建它，而每一次以裸 `git checkout` 开始的重建都悄然丢掉了这些工作。

这个失败有三个阶段，且每一层都掩盖了上一层暴露出的丢失：

1. `git stash push -- ':!profile' ':!node_modules'` 把未落地的修复和定制一起扫进 stash。
2. `git checkout <官方版本>` 覆盖工作树，于是修复离开工作副本，只留在 stash 中。
3. `dsh-plus apply` 重建 `lib/`，它用官方源码覆盖**构建产物**，即便源码已被恢复。

因此源码检查会报告成功，而部署实际是坏的——运行中的 profile 导入的是 `lib/index.js`，不是 `src/*.ts`。每个受影响的包只产出一个打包后的 `lib/index.js`，而不是每个源文件一个文件，所以查找 `lib/icons.js` 既漏掉了改动，又返回空结果，读起来像"不存在"而不是"路径错了"。

## Proposal

把镜像的工作树当作需要保留的数据，而不是可以随意移动的干净检出：

1. 在改动版本之前记录未落地的工作，并按路径恢复，而不是弹出同时装着其它改动的 stash：用 `git diff > <patch>` 记录文件清单，或 `git stash push -- <明确的路径>`。
2. 优先把修复落地到上游并重新钉版本，而不是就地编辑镜像；提交到仓库的改动会存活于每一次重建。
3. 在部署实际加载的层次上验证：在打包后的 `lib/index.js` 中查找改动，并确认该功能对外提供的端点返回预期内容。源码层面的查找不能作为运行中 profile 的证据。
4. 当重建发生在 `apply` 之后时，先重建受影响的包再重启，因为 `apply` 会把官方源码恢复到 `lib/`。

## Acceptance criteria

- 从带有未落地工作的镜像开始的重建，结束时这些工作同时存在于 `src/` 和该包打包后的 `lib/index.js`。
- 验证步骤指明构建产物和对外提供的端点，而不只是源文件。
- 没有任何步骤用裸 `git checkout` 或无路径限定的 `git stash push` 丢弃镜像中的工作。

## Alternatives considered

- **在镜像中保留一个分支，每次重建时 rebase。** 不采用：镜像的版本由发行包的 `sourceBase.revision` 固定，`apply` 拒绝其它检出，因此分支无法承载这些差异。
- **每次重建前复制镜像，再从副本恢复。** 不作为主要机制：副本有数 GB，而记录未落地的 diff 能得到同样结果，且只有几 KB，还指明了覆盖的文件。
- **完全不再编辑镜像，始终先把修复落地到上游。** 采纳为优先做法，但不作为唯一规则：正在抢修的部署无法总是等待发版，因此按路径限定的 stash 让这种情况仍然可恢复。

## Risks

- 要求每个修复先落地再重建会阻塞紧急的本地修复；按路径限定的 stash 与恢复覆盖了这种情况，同时不削弱检查。
- 在打包产物上 grep 会匹配到压缩后的标识符；应查找代码写入的稳定字符串（路径、标记常量），而不是内部函数名。
