# Agent Note：提供方设置中的模型图片输入控件

Status: implemented

[English](2026-08-16-model-image-input-settings-control.md) | 中文

## 问题

pi-ai profile 已允许每个已配置模型声明 `input: [text, image]`，但模型设置页只公开 id、显示名称、上下文窗口和输出上限。用户经由「添加提供方」「添加自定义提供方」或「编辑提供方」配置模型时，没有任何可见入口把模型标记为支持图片。Host 随后会把该模型报告为纯文本，并在请求到达实际支持图片的提供方之前拒绝图片附件、模型选择与 `read_image`。

把该能力留在 settings 文档中没有闭合 Web 流程。模型行本来就是用户描述该模型容量的位置，而兼容的模型列表端点不报告输入模态，因此模型发现和路由 id 都无法提供这项缺失事实。

## 决策

凡是渲染共用 `ModelListEditor` 的提供方流程，每个模型行都会在「模型能力」展开区中显示**支持图片输入**，位置就在上下文窗口与输出上限下方。添加已有提供方、声明自定义提供方和编辑两类提供方都通过同一个组件与同一条持久化路径覆盖。

启用控件会写入模型的显式 `input: [text, image]`；关闭则写入 `input: [text]`。关闭状态必须显式写入而非删除 `input`，因为缺少模型级声明时可能继承支持图片的路由默认值或已安装 catalog 条目。模型行 patch 会保留精选编辑集合以外的所有字段，因此切换图片能力不能删除 reasoning、compatibility 或未来的模型元数据。

模型发现不会预选该控件。OpenAI 兼容模型列表会返回身份信息，有时也返回容量，但不提供模态事实；只有用户可以为采纳的模型声明图片输入。路由级 `defaultInput` 仍保留为 settings 文档选项，供部署有意为每个未描述模型设置同一回退能力。

手写 DeepSeek 适配器的独立模型编辑器继续保持纯文本，因为该适配器按设计拒绝图片内容。在那里显示可写的图片声明，会让 UI 承诺 runtime 无法分派的能力。

## 曾考虑的替代方案

- **继续只在 settings 文档中配置图片能力。** 否决，因为所有常规提供方流程都已在 Web 编辑器中提供，缺少该控件会让 Web 用户只能填写不完整的模型定义。
- **只提供路由级图片开关。** 否决，因为同一网关可以同时提供纯文本与视觉模型；该能力属于模型行。
- **根据模型名称或列表推断能力。** 否决，因为模型 id 由部署自行定义，而兼容列表响应不报告模态。
- **默认每个模型都支持图片。** 否决，因为错误的正向声明会让图片先进入持久历史，再由提供方拒绝；保守的显式声明可在发送前撤销。
- **公开通用模态多选框。** 否决，因为 pi-ai 当前只支持文本与图片输入；一个二元控件直接表达用户决定，也避免产生无法服务正常文本流程的空列表或纯图片配置。

## 后果

通过任意共用提供方模型行配置的模型，都可以在不离开页面的情况下获得图片能力。保存并重新打开提供方后，控件会从显式声明中恢复；关闭它后，即使路由回退值支持图片，该模型仍恢复为纯文本准入。现有模型在用户操作控件前保持不变，端点发现也不会隐式修改它。

该设置改变模型能力元数据，不改变提示词文本。为确实接受图片的模型启用后，既有附件准入与 pi-ai 转换路径会携带持久图片输入；无需新增请求序列化或 session event。
