# Agent working style

Owner-relationship rules for agents working in this repository. The root [AGENTS.md](../AGENTS.md) links here to stay within its word budget.

- **No sycophancy.** When the owner's reasoning has gaps, point them out fact-based from user experience, maintainability, and ecosystem perspectives; when the owner is right, say so and do not manufacture objections. Praise only when earned by evidence.
- **Report before implementing.** Discovery and planning tasks end with a report and wait for explicit approval to develop; never start implementation on top of a "find/analyze/plan" request, and never install or mutate the owner's environments without named consent.
- **Plugin ownership is decided first.** Before implementation, use [dsh-plugin-ownership-and-distribution](skills/dsh-plugin-ownership-and-distribution/SKILL.md) to decide plugin lifecycle, npm publication, repository ownership, and default composition independently. External candidates still require evidence (repository, maintained version, license, feature fit), and selection and installation require the owner's explicit decision.
- **Never pass `wait: true` to a job read, and never sleep in a loop.** The background-job completion notice arrives on its own, so waiting for it converts a free notification into a silent stall the owner watches. Read a job once without waiting: `running` means do other work and let the notice come back, and no state is worth a second blocking read. The same applies to `gh run watch`, `sleep N` polls, and any command whose only purpose is to observe something that will report itself.
- **No tool call waits longer than about a minute outside an explicit release or build step.** A single call that sleeps, watches, or polls trades the owner's time for information that a status read returns immediately. Ask "what would I do with the result?" — when the answer is "decide whether to wait more", the call is the wait. Query the state, act on what it says, and come back later; a job that continues while other work proceeds costs nothing, and one the agent blocks on costs everything it blocks.
- **Never poll a long command; start it as a background job and read it when it finishes.** A repeat of `sleep N; check; sleep N; check` costs the owner the whole interval it waits, and the interval is chosen without knowing the real runtime — so it is usually both longer than needed and still too short. The harness reports completion, so the gap between starting work and knowing it finished is the work itself. While a job runs, do the independent steps it does not own; a wait that blocks them is a second cost on top of the first.
- **Measure a slow step before optimizing or accepting it.** Read the timing the tool reports — the gate runner prints per-gate seconds — before calling something slow, before splitting it, and before adding a timeout. A step that is slow because it does real work is not a defect; a command that feels slow because it is being polled at a guessed interval is one this rule removes.
